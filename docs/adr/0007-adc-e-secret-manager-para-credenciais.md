# ADC (sem chave estática) e Secret Manager para credenciais

Hoje a aplicação autentica no GCP com uma chave JSON de service account (`backend/credentials.json`), commitável por engano e sem expiração — e os segredos reais introduzidos pelo SSO (`AZURE_CLIENT_SECRET`, `SESSION_JWT_SECRET`) vivem em texto plano em `backend/.env`. Isso não é aceitável para um painel que vai rodar em dois serviços Cloud Run independentes (ver seção Docker/Cloud Run do README, já implementada nos commits `b6522ee`/`d914a06`/`1d77c53`/`be38521` — esta ADR não mexe nisso): uma chave estática nunca expira sozinha e uma vez vazada precisa ser revogada manualmente; segredos em `.env` ficam no disco de qualquer ambiente que rode a aplicação.

Decidimos eliminar completamente o caminho de chave estática — em dev e em produção, sem fallback — e mover os dois segredos reais para o Secret Manager.

## Application Default Credentials, sem exceção

`backend/src/services/gcpAuth.js` deixa de passar `keyFile` para `GoogleAuth`; a biblioteca resolve a credencial sozinha pela cadeia padrão do ADC. Em produção isso já cai no metadata server do Cloud Run (a SA é anexada diretamente ao serviço via `gcloud run deploy --service-account=...`, como o README já documentava). Em dev local, o desenvolvedor roda `gcloud auth application-default login --impersonate-service-account=SA@agentspace-469418.iam.gserviceaccount.com` — a mesma SA que já concentra as roles do painel (`discoveryengine.agentspaceAdmin`, `iam.securityAdmin`, `iam.roleAdmin`, `bigquery.jobUser`, `bigquery.dataViewer`) continua sendo a única identidade usada para falar com as APIs do GCP, em dev e produção. O desenvolvedor não ganha essas roles na própria conta — só `roles/iam.serviceAccountTokenCreator` sobre a SA, concedido uma vez, que autoriza a impersonation.

`backend/credentials.json` e a variável `GOOGLE_APPLICATION_CREDENTIALS` saem do `backend/.env.example`. No Docker Compose local, o volume que hoje monta `backend/credentials.json` passa a montar só o arquivo ADC do host (`~/.config/gcloud/application_default_credentials.json:/secrets/adc.json:ro`), com `GOOGLE_APPLICATION_CREDENTIALS=/secrets/adc.json` apontando para ele dentro do container — o container não tem metadata server, então ainda precisa de um arquivo de credencial explícito, só que agora é a ADC do dev (via impersonation), não mais uma chave de SA sem expiração.

## Secret Manager para AZURE_CLIENT_SECRET e SESSION_JWT_SECRET

Os dois segredos reais passam a viver no Secret Manager do projeto `agentspace-469418`, sempre referenciados por `:latest`, com o nome do secret igual ao nome da env var: `AZURE_CLIENT_SECRET`, `SESSION_JWT_SECRET`. A mesma SA (impersonada em dev, anexada em produção) recebe `roles/secretmanager.secretAccessor` nos dois.

> **Atualização (primeiro deploy):** a versão original desta ADR recomendava separar cada segredo por ambiente (dois valores de Client Secret no Entra ID, um secret por ambiente no Secret Manager). Na hora de fazer o primeiro deploy, decidiu-se por simplicidade usar **um único secret de cada, compartilhado entre dev e produção**. Isso é um débito técnico deliberado, não uma mudança de mecanismo: o código (`secretManager.js`, a regra "env var presente usa direto, ausente busca por ID") é idêntico nos dois cenários — só muda quantos secrets existem no Secret Manager e o valor de `AZURE_CLIENT_SECRET_ID`/`SESSION_JWT_SECRET_ID` em `backend/.env`. Migrar para secrets separados por ambiente no futuro é só criar `AZURE_CLIENT_SECRET_PROD`/`SESSION_JWT_SECRET_PROD` e apontar o `--update-secrets` do deploy de produção pra eles — nenhuma mudança de código necessária.

> **Atualização (escopo dos secrets):** `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` e `AZURE_ALLOWED_GROUP_ID` — que esta ADR originalmente tratava como config não sensível, direto em `backend/.env`/`--set-env-vars` — foram promovidos ao Secret Manager também, seguindo exatamente o mesmo mecanismo de `AZURE_CLIENT_SECRET`/`SESSION_JWT_SECRET` (`resolveSecret()` não diferencia "segredo de verdade" de "config só centralizada aqui"). `resolveAppSecrets()` passa a resolver os 5; `GCP_PROJECT_ID` continua de fora do código de resolução — precisa estar disponível *antes* de montar o resource name de qualquer secret, então não pode vir de lá (ovo e galinha) — mas já é injetado como secret em produção mesmo assim (ver [`docs/deploy-cloud-run-manual.md`](../deploy-cloud-run-manual.md), que documentou esse padrão de 5-6 secrets antes mesmo do código acompanhar). Motivação: ter os dois mecanismos de configuração (env var direta vs. Secret Manager) coexistindo sem necessidade real de separação por sensibilidade não trazia benefício, só duas formas de fazer a mesma coisa.

A resolução em `backend/src/index.js` (que passa a ser um bootstrap assíncrono, rodando antes de `app.listen()`) segue uma regra única, sem branch explícito por ambiente: se `process.env.AZURE_CLIENT_SECRET` (ou `SESSION_JWT_SECRET`) já vier setado, usa direto — esse é o caminho de produção, onde o próprio Cloud Run injeta o valor como env var via `--update-secrets=AZURE_CLIENT_SECRET=AZURE_CLIENT_SECRET:latest,SESSION_JWT_SECRET=SESSION_JWT_SECRET:latest`, sem nenhuma chamada de API feita pela aplicação. Se a env var vier ausente — caminho de dev local, onde não existe Cloud Run injetando nada — o backend chama a API do Secret Manager (`@google-cloud/secret-manager`) usando a mesma ADC impersonada, buscando o secret cujo ID vem de duas env vars novas em `backend/.env`: `AZURE_CLIENT_SECRET_ID` e `SESSION_JWT_SECRET_ID` (ex.: `AZURE_CLIENT_SECRET`). O código nunca hardcoda nome de secret nem precisa saber em que ambiente está — só lê o ID de onde buscar. Falha na busca (ADC sem permissão, secret inexistente) derruba o processo no boot, com log claro, em vez de deixar o painel subir "quebrado" e falhar só no primeiro `/auth/login`.

## Considered Options

- **ADC com a identidade pessoal do dev** (`gcloud auth application-default login`, sem impersonation): descartada — exigiria conceder as 5 roles do painel individualmente à conta de cada desenvolvedor, multiplicando a superfície de IAM por pessoa em vez de mantê-la centralizada numa única SA.
- **Fetch dos segredos sob demanda (lazy)** em vez de bootstrap no boot: descartada — adiar a busca para o primeiro uso esconde erro de configuração (ADC sem permissão, secret errado) até alguém tentar logar, em vez de falhar já no `npm run dev`/deploy.
- **Backend sempre chamando a API do Secret Manager, inclusive em produção** (ignorando o `--update-secrets` do Cloud Run): descartada — redundante em produção, já que o Cloud Run injeta o valor de qualquer forma, e adicionaria uma dependência de rede a mais no boot de produção sem necessidade.
- **Nome do secret hardcoded por convenção no código** (sufixo `-dev` automático) em vez de env var explícita: descartada para manter a convenção de nomes explícita na configuração (`*_SECRET_ID` em `.env`), não implícita no código.
- **Dois App Registrations completos** (um por ambiente) em vez de dois Client Secrets no mesmo app: descartada — dobraria o cadastro e a manutenção junto ao time de AD (2 apps, 2 conjuntos de redirect URIs) sem necessidade, já que só o *valor* do secret precisa diferir por ambiente.
- **Versão numérica fixa do secret** em vez de `:latest`: descartada como padrão — mais auditável (sempre se sabe exatamente qual valor está em uso), mas exige atualizar o número em algum lugar a cada rotação; pode virar uma decisão futura se auditoria de versão for necessária.
- **Montar `~/.config/gcloud` inteiro no container** em vez de só o arquivo ADC: descartada — exporia ao container todo o config do gcloud CLI do host (tokens de outras contas/projetos), não só a credencial necessária.

## Consequences

- Um desenvolvedor novo precisa do gcloud CLI instalado e de duas concessões prévias antes de rodar a aplicação: `roles/iam.serviceAccountTokenCreator` sobre a SA (para impersonation) e `roles/secretmanager.secretAccessor` implícito via essa mesma SA (para os secrets) — ambas de responsabilidade de quem já distribuía `credentials.json` hoje.
- `backend/.env` local nunca mais tem `AZURE_CLIENT_SECRET`/`SESSION_JWT_SECRET` em texto plano — só os `*_SECRET_ID`, que não são sensíveis (são só nomes de recursos, não valores).
- Revogar acesso de um desenvolvedor passa a ser revogar `iam.serviceAccountTokenCreator` na SA (ou a sessão `gcloud auth` dele), não mais "invalidar uma chave JSON que pode ter sido copiada para qualquer lugar" — melhora o raio de revogação, mas depende da SA continuar sendo a única identidade usada (se um dia se decidir por identidades pessoais, essa ADR precisa ser revisitada).
- Rotacionar `AZURE_CLIENT_SECRET` ou `SESSION_JWT_SECRET` vira "gerar nova versão no Secret Manager", sem precisar tocar em `.env`/redeploy manual de variável — mas como a resolução é sempre `:latest`, não há como saber, só olhando o Secret Manager, qual versão um processo já em execução carregou no boot (só reinicia com o valor novo no próximo start).
