# BigQuery Billing Export (Standard usage cost) como fonte da página de Custos

A nova página de Custos precisa mostrar, com precisão de SKU, quanto o projeto `agentspace-469418` gastou, dividido em duas categorias (Gemini/licenças e Infra da própria aplicação) mais uma terceira de fechamento ("Não Categorizado", ver `CONTEXT.md`). A Cloud Billing API pública (`cloudbilling.googleapis.com`) não oferece isso: `services.skus.list` só devolve preço de tabela público (não consumo real), e a Budgets API só notifica de forma assíncrona via Pub/Sub quando um limiar pré-configurado é cruzado — não existe um endpoint de "consulta sob demanda" para gasto real por SKU. Decidimos consultar diretamente a tabela do **BigQuery Billing Export, variante "Standard usage cost"**, que já estava habilitada na Billing Account "Projetos Editora Globo" (`01779C-55AF20-FD92F6`) antes mesmo desta feature existir, exportando diariamente `infra-bi-355620.billing_standard.gcp_billing_export_v1_01779C_55AF20_FD92F6`. Essa tabela cobre os 71 projetos da Billing Account inteira; a aplicação filtra por `project.id = 'agentspace-469418'` em cada consulta.

A Service Account que a aplicação já usa hoje é reaproveitada (nenhuma SA nova é criada — SAs não existem "na organização", só em projetos, o que originalmente gerou confusão ao tentar criar uma pela tela de IAM da organização). Ela recebe duas permissões novas, ambas escopadas ao mínimo necessário: `roles/bigquery.jobUser` no próprio projeto `agentspace-469418` (roda e paga pelas queries), e `roles/bigquery.dataViewer` só no dataset `billing_standard` (não no projeto `infra-bi-355620` inteiro, que tem dezenas de outros datasets de outras áreas). Nenhuma permissão em nível de organização ou de Billing Account é necessária — o binding de `roles/billing.viewer` cogitado inicialmente foi descartado quando a rota via Cloud Billing API foi abandonada.

As duas categorias (Gemini/Infra) são listas explícitas e nomeadas de `service.description` (ex.: `["Vertex AI Search", "Vertex AI"]` para Gemini, confirmado contra dados reais do Console), mantidas manualmente no código — não uma heurística automática. Qualquer SKU fora das duas listas cai em "Não Categorizado", que existe justamente para que a soma das categorias sempre feche com o total e sirva de alerta para quando um serviço novo precisar ser classificado.

## Considered Options

- **Cloud Billing API (Budgets API + Pub/Sub)**: descartada — é um mecanismo de alerta por limiar, não de consulta sob demanda; exigiria criar Budgets por categoria, um tópico Pub/Sub, um assinante, e um lugar para persistir o último valor recebido (a aplicação não tem banco hoje). Mesmo assim, o valor seria aproximado (por faixas de limiar), nunca exato nem com granularidade de SKU.
- **Views internas de FinOps já existentes no mesmo dataset** (`tbCustoTotal`, `vwResultadoMesAtual`, etc.): descartadas — são mantidas por outro time (dono do projeto `infra-bi-355620`), schema não documentado para nós, podem embutir lógica própria (conversão de moeda, rateio por diretoria) que não necessariamente bate com as categorias Gemini/Infra, e podem mudar sem aviso.
- **Habilitar o export "Detailed usage cost"** (desabilitado, adicionaria granularidade por recurso individual): descartada — a variante "Standard usage cost", já ativa, já tem granularidade de SKU, suficiente para as categorias definidas; a granularidade extra não tem uso conhecido nesta feature.
- **Service Account dedicada só para Custos**: descartada — quebraria o padrão de "uma SA só" que o resto da aplicação segue (`gcpClients.js`), sem ganho de segurança proporcional, já que `bigquery.dataViewer`/`jobUser` são menos sensíveis que `iam.securityAdmin`, role que a SA já tem hoje.

## Consequences

- A feature depende de um dataset (`infra-bi-355620.billing_standard`) que a aplicação não controla — se o time dono desabilitar o export "Standard usage cost" ou mudar o nome/local da tabela, a página de Custos quebra sem aviso prévio da nossa parte.
- As listas de `service.description` por categoria são mantidas manualmente no código; um serviço de billing novo (ex. se a aplicação passar a usar Cloud Storage) aparece em "Não Categorizado" até alguém atualizar a lista — comportamento esperado, não um bug.
- Dados só são atualizados 1x/dia pelo próprio GCP; a página nunca mostra gasto "em tempo real", e o cache do backend (TTL de horas, mais botão manual de atualizar) reflete isso deliberadamente.
